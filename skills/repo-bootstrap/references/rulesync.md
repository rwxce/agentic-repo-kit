# rulesync — single source for every agent tool

Docs checked: https://github.com/dyoshikawa/rulesync — already does it? **yes**: one `.rulesync/`
directory generates rules, ignore, MCP, commands, subagents, skills, hooks, permissions (and
checks for some targets) for dozens of tools. Re-read its README/changelog at run time: targets
and feature support change often between majors.

## When to propose it
- Recommended by default: 2+ agent tools in the team, or likely to be.
- Native files only: a single tool forever and a very small config.

## Setup
1. Version: pick the newest release published **≥5 days ago** (`npm view rulesync time --json`) and
   pin it exactly as a dev dependency. Do not copy a version from this file.
2. Scripts: `"rulesync": "rulesync generate"` and `"rulesync:check": "rulesync generate --check"`
   (confirm the exact check flag/command in the current docs).
3. Config `rulesync.jsonc`:
```jsonc
{
  "$schema": "https://github.com/dyoshikawa/rulesync/releases/latest/download/config-schema.json",
  // Edit only .rulesync/, then run the generator. Generated files are tracked but never hand-edited.
  "targets": {
    "claudecode": ["rules", "ignore", "mcp", "commands", "subagents", "skills", "hooks", "permissions"],
    "cursor":     ["rules", "ignore", "mcp", "commands", "subagents", "skills", "hooks", "permissions"]
    // add codexcli, opencode, copilot, geminicli… per the team's tools
  },
  "outputRoots": ["."],
  // Keep false until you confirm it never deletes hand-maintained tool-specific files.
  "delete": false
}
```
4. Layout:
```
.rulesync/
  rules/          root rules (→ CLAUDE.md, AGENTS.md, .cursor/rules…)
  subagents/      agents
  skills/<name>/  SKILL.md + references/
  commands/       slash commands (aliases of skills where possible)
  hooks.json      hook wiring
  permissions.jsonc
  mcp.json        shared MCP servers (secrets via ${VAR})
  checks/         review checklists (only some targets emit them; skills can read them directly)
```
5. Root rule header: "AI editor config is generated by rulesync. Edit only `.rulesync/`, then run
   the generator. Never hand-edit generated files. CI enforces this."
6. CI: run `rulesync:check` in the main CI job (template `ci/ci.yml`).

## Migrating existing loose config (audit mode)
- Import with the tool's import command into `.rulesync/`, or move files by hand.
- Before deleting the old files, fill the trim-with-audit table for anything not carried over.
- Generate, diff the generated output against the old files, explain every difference.

## Gotchas seen in practice
- A feature not supported for a target (e.g. `checks` for Claude Code in some versions) is silently
  skipped — keep a comment in `rulesync.jsonc` and make the consuming skill read the source file.
- Majors can change generated paths; upgrade in a dedicated PR with a full diff review.
- Hooks generated for several tools must use commands every tool can run; tools that cannot "ask"
  may need a shim that turns `ask` into a rejection.
