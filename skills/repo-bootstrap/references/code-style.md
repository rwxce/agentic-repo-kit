# Phase 2 — code style: follow it, or refactor without changing behavior

## Measure first
From Lens 5 (or a quick sample if the lens was skipped):
- Configured tooling: formatter (Prettier, Biome, Black, gofmt, rustfmt…), linter and its rule set,
  editorconfig, typecheck strictness. Is it enforced in CI or only local?
- Dominant style by sampling ~20 files across layers: quotes, semicolons, indentation, line length,
  naming (files, components, functions, constants), import order, export style (default vs named),
  error-handling idiom, comment density.
- Inconsistencies with counts: "single quotes 82% (41 files), double 18% (9 files: a.ts:1, …)".
- Structural debt that hurts agents: god files (>800 lines), duplicated helpers, dead exports
  (if a dead-code tool exists, run it read-only), cycles.

Present a short table: Dimension | Dominant | Share | Outliers | Enforced?

## Option (a) — follow the existing style
- Encode the dominant style in the formatter/linter config so the agent cannot drift.
- Add the non-mechanical conventions (error idiom, house helpers, naming) to the Build rules of
  the relevant implementer agents and to the root rules (one line each, no essays).
- If the formatter is not enforced in CI, propose a CI check — format-check only, no reformat PR.
- No source changes.

## Option (b) — behavior-preserving refactor (separate plan, separate PRs)
Never mixed into the bootstrap PRs. The plan contains:

1. **Safety net first** — characterization tests for every module to be touched that lacks tests
   (assert current outputs, including odd ones). Record the baseline: tests green, typecheck,
   build, and for UI screenshots at the agreed breakpoints.
2. **Mechanical PR** — formatter/import-order only, generated by the tool, no hand edits. Add the
   commit hash to `.git-blame-ignore-revs`.
3. **Per-module refactor PRs**, small and ordered by risk (lowest first). Each states: what
   changes structurally, what must stay identical, and evidence (same test results, same typecheck,
   same screenshots, same public API — exported symbols diff empty unless intended).
4. **Lint rules start as `warn`**, flipped to `error` once the code complies, so the refactor is
   enforced afterwards.
5. **Out of scope by rule**: bug fixes found along the way go to follow-up issues, not into the
   refactor PR (a refactor PR that changes behavior can't be reviewed as a refactor).

Rough sizing goes into the plan (files, PR count) so the user can choose (a) for now and (b) later.

## Option (c) — leave it alone
Record the decision in the proposal; still mention the top 3 inconsistencies so the choice is
informed.
