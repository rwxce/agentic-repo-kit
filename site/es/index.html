01 / El problema

Los agentes de código programan antes de planificar.

Hacen ingeniería a medida cuando ya existe un SDK o un import, se les escapan efectos secundarios entre sistemas, dan el trabajo por terminado cuando pasan tests con mocks y acumulan configuración inflada. Cada guardrail de este kit se añadió tras un fallo concreto en el código de un SaaS real.

3–6 de 18

efectos secundarios que se le escapan a cada planificador sin el protocolo. Ninguno consultó la documentación del proveedor.

~17 de 18

efectos secundarios encontrados con el pipeline completo.

Un protocolo escrito gana a un modelo más grande.

Un modelo más barato con el protocolo de planificación encontró casi tantos efectos secundarios como el más caro.

02 / Cómo funciona

No se escribe nada hasta que dices adelante.

  1. entender
  2. diseñar
  3. elegir conceptos
  4. diseñar controles
  5. generar
  6. verificar
  7. aprender

Fases 0–1

Entiende

Escanea el repo y pregunta: objetivo, familias, herramientas, estilo de código y profundidad. Un proyecto nuevo pasa una entrevista corta. Uno existente, lentes de descubrimiento en paralelo, una decisión de estilo de código y un benchmark de una funcionalidad grande en contextos limpios.

Fase 1b

Diseña

Un diseño de sistema a la medida del riesgo: requisitos, fronteras de confianza, riesgos y 2–4 alternativas comparadas con criterios comprobables. Un ADR por decisión. En un proyecto nuevo, el diseño también espera tu luz verde.

Fase 4

Elige conceptos

Las señales del repo apuntan a fichas de conceptos, como webhooks, migraciones o copias de seguridad. Si el «cuándo no» de una ficha encaja con tu repo, se descarta.

Fase 4

Diseña controles

Cada decisión y cada concepto se convierte en un check: un hook, una regla de lint, un test o un paso de CI, con pruebas file:line. Después espera tu luz verde.

Fase 5

Genera

Subagentes en paralelo convierten la propuesta aprobada en pull requests.

Fase 6

Verifica

Tests, hooks disparados de verdad, ejecuciones de CI, el benchmark repetido y revisión adversarial.

Después

Aprende

La skill reflect que se instala convierte tus correcciones en checks que fallan cuando el error se repite. Las reglas en prosa son el último recurso.

/repo-bootstrap Pregunta qué quieres y después propone.
/repo-bootstrap quick Se salta el benchmark.
/repo-bootstrap audit Audita y mejora una configuración de agentes existente.

03 / Diseño y conceptos

Cada decisión dice qué check la sostiene.

Antes de proponer ningún hook, el kit averigua qué necesita tu proyecto y cómo se hará cumplir cada elección. La profundidad va según el riesgo: a una CLI local le basta una página; un SaaS con pagos incluye modelado de amenazas.

Diseño de sistema

A la medida del riesgo

Ligero, estándar o profundo, según lo que haya encontrado el descubrimiento. Cada decisión abierta tiene 2–4 alternativas comparadas con criterios que cualquiera puede volver a comprobar: actividad de mantenimiento, licencia, CVE de la versión exacta, cambios incompatibles, coste modelado y dependencia del proveedor. Nunca estrellas ni notas sobre 10. Cada decisión queda en un ADR con la línea «Enforced by». En un repo existente, documenta el diseño real con file:line y solo propone migrar con pruebas y tu luz verde.

Catálogo de conceptos

51 conceptos, bajo demanda

Desde webhooks y migraciones de esquema hasta pools de conexiones, sagas, copias de seguridad con restauración probada y SLO. Cada ficha dice cuándo aplica, cuándo no y qué check la verifica. Una tabla relaciona lo que muestra el repo con las fichas que vale la pena abrir. Las que aún no se han probado en producción lo dicen, y sus checks se proponen como algo por validar.

Herramientas recomendadas

De terceros, con cuarentena

Skills, CLI y servidores MCP que el kit propone pero no incluye, cada uno con su origen, la versión probada y la licencia. Antes de instalar nada, lee sus archivos, te dice qué ejecutan y a qué pueden acceder, y espera tu OK.

Módulos de producto

Opcionales, solo con una señal

Diseño (documentos de producto y diseño, tokens, inventario de UI), legal (un inventario hecho desde el código y preguntas para ti), contenido y changelog, copy y glosario de traducción, IA de producto, planes como datos y un lanzador de desarrollo local. Cada uno se ofrece solo cuando el repo muestra la superficie que cubre, con checks sin dependencias. El módulo legal nunca escribe el texto legal definitivo.

04 / Qué puede montar

Once familias. Elígelas todas o solo una.

Funciona con Claude Code, Cursor, Codex CLI, OpenCode, Copilot, Gemini CLI y otros, con rulesync como fuente única o con archivos nativos. OpenCode tiene shims para los hooks que no puede ejecutar tal cual.

Reglas raíz

Plan antes del código, documentación primero, dependencias fijadas, validación por caso de uso en cada paso, verificación de principio a fin.

Agentes

Roles de orquestador, implementador y revisor, implementadores por dominio.

Skills

plan-feature, verify-integration, debugging, pr-review y reflect, que convierte las correcciones repetidas en checks.

Hooks

Bloqueo de escrituras hacia fuera, control de comandos peligrosos, lint en cada cambio, comprobación previa de PR, un sello de revisión ligado a la huella del diff, traspaso entre sesiones, un cortafuegos Unicode.

Tests de arquitectura

Sincronía entre registro y sistema de archivos, códigos únicos, paridad de i18n, una guarda de layout que recorre anchos en un navegador real.

Lint propio

Límites entre capas, sin ciclos, pasarelas de SDK, tests junto al código. Adaptadores para Swift, Kotlin, Python, Go, Rust y Dart.

CI

Sincronía de la configuración de IA, lint, typecheck y tests, tests guarda en cada PR, build del artefacto real, comprobaciones de paridad, guarda de la política de ramas.

Automatizaciones

Preparación del espacio de trabajo, un flujo de release endurecido, Renovate con una edad mínima de publicación, control de versiones de las skills incluidas.

Permisos

Capas deny, ask y allow para la shell, los secretos y las acciones hacia fuera. Instalar algo de terceros siempre pide permiso.

Registros

Registro de efectos secundarios, inventario del blueprint, variables de entorno.

Servidores MCP

Servidores oficiales separados entre prod y sandbox. Los que no tienen la versión fijada quedan marcados. Se proponen, nunca se instalan sin aprobación.

05 / Preguntas

Antes de ejecutarlo.

¿Funciona sin rulesync?

Sí. Elige “native files only” en la fase 0 y escribe directamente los archivos de .claude/ (o los de tu herramienta).

¿Reescribirá mi código?

Solo si eliges el refactor que preserva el comportamiento. Incluso entonces hace un plan aparte, con tests de caracterización primero y PR pequeñas.

¿Cuánto cuesta?

Una ejecución rápida son unos 60–120k tokens. El benchmark completo añade unos 200–300k. El benchmark es el paso que encuentra los huecos reales, así que se recomienda para repos que manejan dinero, autenticación o datos personales.

¿Instala servidores MCP?

No. Propone servidores oficiales con sus comandos de instalación y espera tu OK para cada uno. Las skills y herramientas de terceros pasan antes por una cuarentena: lee su contenido y te dice qué ejecutan y a qué pueden acceder antes de pedirte nada.

¿Solo sirve para repos de TypeScript?

No. Las plantillas usan TypeScript como referencia, y los adaptadores por lenguaje llevan cada guarda a las herramientas de Swift, Kotlin, Python, Go, Rust y Dart. Los adaptadores están documentados, pero aún no se han probado de principio a fin.

¿Con qué licencia se distribuye?

MIT. Las plantillas adaptadas de otros proyectos conservan su crédito, recogido en THIRD_PARTY.md.

O simplemente dilo: prepara este repo para agentes.
